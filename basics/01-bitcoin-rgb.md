# 比特币 & RGB 协议

---

## 为什么比特币"不可编程"

比特币本质是一个**只记转账的账本**。它的脚本语言极度简化——故意设计成不能循环、不能读外部数据、不能存状态。

**设计原因**：安全第一，越简单越难被攻击。

**对比以太坊**：以太坊在账本里存代码和状态，全网节点一起跑，账本变成"全球共享的计算机"。

---

## RGB 协议是什么

在比特币上实现智能合约功能的协议，**比特币本身一行代码没改**。

核心思路：**不让全网验证，只让交易当事人验证。**

---

## OP_RETURN

比特币交易里允许塞入少量任意数据（最多80字节）的字段。

```
比特币网络不理解、不验证这段数据，只是帮你存进区块
```

RGB 把合约状态的**哈希值**塞进 OP_RETURN，作为链上锚点。

---

## Client-Side Validation

**核心机制**：验证责任在收款方自己，不在全网。

```
发送方给收款方：
  - 完整的代币历史（从创世到现在每一笔）
  - 每笔对应的比特币链上哈希

收款方自己验：
  1. 比特币链上有这些哈希 ✓
  2. 每步转移规则合法 ✓
  3. 最终转到我这里 ✓
  全部通过 → 收款确认
```

**类比**：公证处不读合同内容，只盖章证明"某时某人在此盖章，文件哈希是xxxx"。

---

## UTXO与防双花

比特币里没有"余额"，只有**未花费的硬币（UTXO）**。每个UTXO只能被花一次，这是比特币最基础的防双花机制。

---

## Single-Use Seal（一次性封印）

RGB 把代币绑定在具体的 UTXO 上。

```
转移代币 = 必须花掉对应的 UTXO
UTXO 只能花一次 → 代币只能转移一次
```

**RGB 直接继承了比特币的防双花能力**，不需要自己重新发明。

打开封印（花掉UTXO）就永久销毁，无法复用。

---

## RGB 的角色分工

| 角色 | 负责什么 |
|------|----------|
| 比特币 | 存哈希锚点（OP_RETURN）+ 防双花（UTXO）|
| RGB 链下 | 代币发行规则、转移逻辑、历史记录 |
| 收款方 | 验证完整历史 |

> 比特币 = 全球最可信的盖章机器，RGB借用它，不改造它。

---

## RGB 的弊端

| 弊端 | 原因 |
|------|------|
| 历史越长验证越慢 | 收款方要验证从创世到现在所有记录 |
| 数据丢了代币废掉 | 历史在链下，用户自己保管 |
| 多方交互极复杂 | 多人需协调链下数据，有人掉线就卡 |
| 无公开账本 | 隐私是双面刃，无法审计 |
| 生态极早期 | 钱包少、交易所不支持、代码未经考验 |

---

## RGB-USDT（Utexo）

- Utexo（前身Tricorn）做了**以太坊 → 比特币的跨链桥**
- 1:1 锁定以太坊 USDT，在比特币上铸造 RGB-USDT
- Tether 投资750万美元：战略投资，争夺比特币稳定币标准主导权
- **意义**：比特币生态第一次有了原生稳定币，DeFi、支付成为可能
